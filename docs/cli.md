# Command-line contract

This is the contract that callers, including the bundled agent skill, rely on: what each command reads and returns, its output records, and its exit codes. Each option's meaning is in `sessidx COMMAND --help`.

## Output and exit codes

Every command emits JSON Lines on stdout, except help/version text and the help that `sessidx` with no arguments prints, which exits 2. Data records carry `type`: `session` for search (with `hits`), `hit` for grep, `record` for show, `count`, `row` for SQL (columns inside `data`, preserving a column named `type`), `index`, or `doctor`. Select data before using `jq`, for example `jq -c 'select(.type == "record") | .record.message'`.

One final `end` record contains `complete`, `stale`, `next`, `searched`, `unavailable_ranges`, and refresh coverage in `refresh`. A result limit, the page size, a deadline, an unavailable range, or a stale refresh makes `complete=false`; parse errors and deferred tails are reported in `refresh` without changing it. `stale` is `false` when the command's refresh reached every source before it answered, `true` when it did not, and `null` when nothing compared the index with the sources: `sql`, which does not refresh, and errors.

The data lines of a `search`, `grep`, or `show` page total at most 24 KiB, so the `end` record arrives within what Claude Code, Codex, and Pi show an agent from one command. A record that does not fit after others starts the next page. A `grep` or `show` record that does not fit alone carries `part`, a piece of the redacted record's JSON text, instead of `record`, and `"cut":[{"field":"/part","bytes":B,"offset":O,"kept":K}]`: the whole JSON text is `B` bytes and the page holds `K` of them from `O`, ending on a UTF-8 boundary. `show` continues through `next` with the following piece until the text is whole, so joining the `part` values in order gives JSON that parses to the record. A `search` session that does not fit has its hit texts shortened to one common length, each listed in `cut` by its JSON Pointer `field`, such as `/hits/0/text`. `search` and `grep` go on to the next session or hit; `show REF --around 0` reads a cut hit whole. `sql`, `count`, and `doctor` output is not paged.

`searched.returned` is the number of data records written (for `index`, the source records it indexed). `searched.records` counts the unit that `searched.unit` names, as observed, not as an estimate of SQLite pages or of all underlying events examined:

- `session_hits` (`search`): hits inside the returned sessions.
- `source_ranges` (`grep`, `show`): attempted ranges; `searched.bytes` is the total read from those that could be read.
- `aggregate_rows` (`count`) and `sql_rows` (`sql`).
- `source_records` (`index`).
- `diagnostic` (`doctor`), which counts none.

`refresh` reports:

- `records` and `files_changed`: what this run indexed.
- `deferred_tails`: files whose final record still awaits its newline.
- `parse_errors`: the total over the whole index.
- `missing_roots` (see [Sources and database](#sources-and-database)), `writer_busy`, and `stale`.
- `continuation`: the file where a budget-limited refresh stopped.

`sql` does not refresh, so its `refresh` holds only `stale`, which is `null`, and `writer_busy`.

Exit codes are 0 for data, 1 for no data, and 2 for errors. A complete empty result and an incomplete one are distinguished by `end.complete`. Errors produce one `end` record with `error`, `complete=false`, `stale=null` (unknown), `next=null`, and zero `searched` counts, without refresh coverage. Any recovery instruction is in `error`, never only on stderr. A reader that closes stdout early, such as `head`, ends the command quietly with exit 0. Successful maintenance exits 0; an `index` run that leaves the index stale (writer busy, or a previously indexed root missing) exits 2 with its normal records and no `error`.

## Sources and database

The default database is `~/.cache/sessidx/index.db`. Discovery reads `~/.claude/projects`, `~/.codex/sessions`, `~/.codex/archived_sessions` (where Codex moves an archived thread's file), and `~/.pi/agent/sessions`; a root that is itself a symbolic link to a directory is followed, but links inside a root are not. Session files are `*.jsonl`, and Codex's compressed `*.jsonl.zst` rollouts are reported under their `.jsonl` path, which may not exist on disk; read such a record with `show`. A root you do not have, such as an agent you do not use or the Codex archive before the first archived thread, is skipped; `end.refresh.missing_roots` lists each absent root as the `AGENT=PATH` that `--root` accepts. A root that disappears after its sessions were indexed (moved or unmounted) keeps its rows and makes refreshes stale until it returns, and `index --full` refuses to run until it is restored or left out of `--root`. `--db PATH` selects another database and repeatable `--root AGENT=PATH` replaces all default roots, so pass both Codex directories to keep archived threads; later commands, including the recovery commands below, need the same flags. An older schema fails with one recovery instruction: `run sessidx index --full`.

## Sessions

A session is one transcript file, identified by the agent's native ID from that transcript's own header or name, never from history copied into it: the Codex thread ID in its first `session_meta`, the Pi ID in its session header, the Claude session ID that names a main transcript, or the `agentId` of a Claude subagent transcript, whose `parent_id` is the session that spawned it. A copied event belongs to the transcript it appears in; counts still use only its first copy. `session_kind` is `main` for a session started on its own and `subagent` for one spawned by another session of the same agent, from native evidence only: Claude `agentId` or `isSidechain`, Codex `session_meta.source`, and Pi, which has no subagents; otherwise it is `unknown`. `cwd` is the directory the session started in, and `started_at` its first timestamp. One ID can name more than one transcript: Claude agent IDs are unique only within their parent session, and Codex can continue a thread in a second rollout file. A session selector (`--session`, or a `show` target) that names more than one transcript fails and lists their paths; pass one of them instead. One that names no indexed transcript fails too, with an error that names it: a selector is a whole session ID, transcript path, or `codex://threads/` link, never a prefix; a transcript that is not indexed yet, which `index` finishes, or that was deleted is named by none; and `search` or `sql` finds an indexed session's ID.

## Commands

### search

`search` uses ranked full-text search (SQLite FTS5) and returns one record per session. Sessions are ordered by the best hit's BM25 relevance, then the latest matching hit timestamp (newest first); index order breaks remaining ties. Each record carries the session's `agent`, `session_id`, `session_kind`, `parent_id`, `path`, `cwd`, and `started_at`, up to three best hits in relevance/recency order, and `matched_hits`, the number of matching indexed events. Each hit carries its `ref`, `ts`, `role`, `model`, and matched `text`. The session limit is applied before selecting its hits. Whitespace-separated terms are joined with AND; quoted phrases preserve word order. Chinese character sequences use phrase matching; Latin terms match whole words. Full-text search covers redacted messages, tool inputs, and the first 2 KiB of tool result or diagnostic attachment text. Prefixes stop at a UTF-8 boundary and report `truncated` when text was omitted. Lookup identifiers (absolute, relative and dotfile paths and `path:line` locators, versioned names such as model IDs, hex, UUIDs, code identifiers and command-line flags) stay searchable. A search that runs longer than two seconds fails, because a ranked page cannot be partial; its error says to run `sessidx index` when most of the index was written since it was last compacted, and otherwise to search again and then add distinctive terms. Filters do not shorten a search, because each match is read before they apply.

### grep and show

`grep` matches regexes over original bytes before redacting its display, so a match can lie in a part of the record that was cut. It requires a narrowing filter other than role or session kind, reads only indexed byte ranges of the selected sessions, a transcript at a time and each in line order, and stops after two seconds or the hit limit; its cursor resumes after the last range it examined, matched or not. `show` expands a hit's `ref` (`path:line`), a session ID, a transcript path, or a `codex://threads/ID` address. Both return the source line as a redacted JSON object in `record`, or as `part` when it does not fit a page alone, once per role, however many events the index derived from it. A range whose source changed since indexing is unavailable until reindexed, and `end.unavailable_ranges` counts it: `grep` cannot match it, and `show` returns its record with `unavailable`, the reason with its recovery instruction, instead of `record`.

### Filters and pagination

Search, grep, and count share the filters listed by `--help`. Filters select results; they do not narrow discovery. Option values are checked before any refresh: an unknown enum value, a `--limit` outside 1–1000, a repeated `--by` grouping, or a malformed `--since`, `--until`, or `--root` exits 2 with an error that names the flag and, for a closed set, lists its valid values; there are no aliases.

`search` and `grep` default to 20 results; `show` defaults to 100. Pagination uses only `--cursor`: pass the opaque string from `end.next` to the same command and filters. Later pages include only events indexed before the first page. Search pagination covers the first 100 ranked sessions, whose order the cursor freezes; once a page reaches that bound while more sessions match, the end record has `complete=false` and no `next`, so narrow the query to reach the rest. Appends are allowed. A changed query, a rebuild, or a replacement or deletion of a transcript the later pages would read requires restarting without the cursor: for `grep`, the transcript it stopped in or one after it (transcripts are read in the order in which they were indexed); for `search`, a session it has not returned yet; for `show`, a replacement of its transcript. A `show` whose transcript was deleted fails as an unmatched selector instead. Limits bound returned rows, not SQLite's work.

### count

`count METRIC` accepts `commands`, `failures`, `denials`, `usage`, or `compactions`. Each row names its `metric`, its groups, the selected `program` if any, and counts named for what they count; the counts of a metric partition its population, and anything outside the population has a name of its own:

- `commands` counts static shell syntax sites in tool calls: `sites` that parsed, of which `sites_without_program` have no literal program word (such as `$CMD args`) or one that redaction withheld. `unparsed_calls` counts the shell calls whose syntax did not parse, which are outside `sites` because their sites are unknown. With `--program`, `matching_sites` is the part of `sites` that runs the program. Sites do not prove execution.
- `failures` counts native tool-call attempts: `calls` = `failed` + `succeeded` + `outcome_unknown`, where a call whose result carries no failure or success evidence has an unknown outcome rather than a successful one. With `--program`, `calls` holds the calls whose shell syntax names the program, and `calls_with_unresolved_program` counts the other calls with a site whose program is unknown, which might run it.
- `denials` counts native tool-result events: `results`, of which `denied` carry denial evidence, of which `denied_reason_unknown` have a denial whose reason is unknown. With `--program`, `results` holds the results of calls that name the program, and `results_with_unresolved_program` the other results whose call has a site whose program is unknown.
- `usage` counts model requests recorded with token usage: `requests`, each once under its own model, and `passes`, the model passes they ran, each under the pass's model, so an advisor's model can have passes and no requests. A request whose record lists fewer than two passes is one pass. The token sums `input`, `cache_read`, `cache_write` (of which `cache_write_5m` and `cache_write_1h` where the record splits it), `output`, and `reasoning` (part of `output`) add up over passes; `input` excludes cached and cache-written tokens, so `input` + `cache_read` + `cache_write` is the prompt. Input and output are recorded by every pass; `cache_read_recorded`, `cache_write_recorded`, `cache_write_5m_recorded`, `cache_write_1h_recorded`, and `reasoning_recorded` count the passes that record the others. Copied Codex running totals from builds that wrote no per-request record count as requests of the transcript that copied them. A call that no record states as a request of its own, such as one that writes a compaction's summary, is outside the population.
- `compactions` counts context compactions: `compactions` = `auto` + `manual` + `trigger_unknown`, with `pre_tokens` and `post_tokens`, the context sizes before and after, summed over the `pre_tokens_recorded` and `post_tokens_recorded` compactions that state them. A compaction's `model` is the session's model when it happened.

`failures` counts tool calls and `denials` counts tool-result events; a call that runs several shell commands contributes once to each, not once per command. `--by` takes a comma-separated subset of `agent`, `model`, `role`, `week` (UTC ISO week), and `session_kind`; the default is `agent,model,role,week`, or `agent,model,week` for `usage` and `compactions`, `--by` with no value returns one total row, and an empty value, an empty segment, or a repeated name is an error. Requests and compactions have no speaker and run no program, so `--by role`, `--role`, and `--program` are errors for `usage` and `compactions`. Native IDs deduplicate history; identical text and retries remain separate. Unknown models and session kinds stay explicit. `count` uses canonical events; `doctor` counts stored rows, including inherited copies and context.

### sql

`sql` opens the database read-only without refresh, accepts one SELECT/WITH, and fails instead of returning partial success above 10,000 rows or two seconds. Query `sessions`, `events`, `canonical_events`, `call_outcomes`, `commands`, `denials`, `requests`, `request_passes`, `request_errors`, and `compactions`, defined in [`src/schema.sql`](../src/schema.sql); the other tables are index storage.

#### Events, outcomes, and transcripts

`call_outcomes` has one row per canonical tool call with its outcome: `ok` is 0, 1, or NULL when unknown, as `count failures` classifies it. `events` carries each event's `agent`, `session_id`, `file_id`, `path`, and `canonical` (1 for the first copy of its native event, which counts use), and reads `text` only when a query names it; in `canonical_events`, a Claude message written as several records carries the text of all of them, joined by newlines. `sessions` carries each transcript's earliest and latest indexed event timestamps in `min_ts` and `max_ts`; the logs can hold later events not indexed yet, so `max_ts` does not show that a session ended. For per-transcript correlation with `sessions`, use `e.file_id = s.file_id` or the indexed `e.path = s.path`; `(agent, session_id)` can name several transcripts and combines their events.

#### Denials

`denials` carries one row per recognized denial: `source` names the channel (`hook`, `batch_hook`, `guard`, `marker`, `native_denial`, `permission_rule`, `user_rejected`, `classifier`, or `classifier_unavailable`); `class` is the denial's class (`policy`, `coverage`, `error`) or `unknown`; `producer` is the producer a reason marker names, or NULL when no marker declared one or redaction withheld it; `reason_id` names the rule by the producer's own ID from a marker, or for the frozen legacy wording by agent-guard's public ID (the earlier dotfiles guards' name for a rule only they had), with `unknown` for unmapped text, sentences shared by several kinds, and withheld markers; historical wordings of the same rule share an ID. A row with NULL `producer` and a known `reason_id` was inferred from the frozen wording of agent-guard or the earlier dotfiles guards, so a query spanning logs before and after markers includes those rows explicitly, as in `producer = 'agent-guard' OR (producer IS NULL AND reason_id <> 'unknown')`, which leaves out the shared sentences.

#### Requests and passes

`requests` has one row per model request with the token columns `count usage` sums, taken from one of its records: a finished one when any is (`finished` is 0 otherwise), in the transcript that ranks first by session start and path, and the last of those there; the request belongs to that record's transcript, and `native_id` is NULL for a Codex running total. Its `route` is the evidence that record states of where the request was sent, which does not establish how it was billed, and `route_source` names the field: `message.id` for the prefix of a Claude message ID before its last `_` (`msg` for Anthropic's API, `msg_vrtx` for Vertex), `session_meta.model_provider` for the provider a Codex rollout's header names, `message.provider` for a Pi entry's provider; both are NULL without evidence. `stop_reason` is the reason the record states, in Claude's or Pi's words, and NULL for Codex. `request_passes` has one row per pass, numbered by `pass`: a request's own row as pass 0 with NULL `kind` when its record lists fewer than two passes, and otherwise each pass with its `kind` and `model`, whose `reasoning` the record does not state, and with its request's `route` and `route_source`.

#### Request errors

`request_errors` has one row per first copy of a record that states a model request failed, named by `source`: `api_error` for an attempt Claude Code retries, with its `retry_attempt` and either the HTTP `status` or the connection failure's `code`; `api_error_message` for a failure Claude Code reported, with its category in `code` and any `status`; `stop_reason` for a Pi request that ended in an error, which is also a `requests` row. A Pi request the user aborted is not a failure, and Codex records none. `model` is the session's model when the request failed, NULL before its first response, and `route` the record's own evidence (`error.requestId` or `requestId` prefixes for Claude), or NULL. The rows are reports, not a part of `requests`: a retried attempt can end in a request, so an error rate does not divide them by `requests`; the share of Pi requests that failed is `stop_reason = 'error'` within `requests`.

#### Compactions

`compactions` has one row per first copy of a compaction with its `trigger` (`auto`, `manual`, or `unknown`), context sizes, for Codex the `request_id` of the `requests` row that wrote it, and, for Pi, the usage of the calls that wrote its summary in `summary_input`, `summary_output`, `summary_cache_read`, and `summary_cache_write`, which `count usage` does not include.

#### Shell arguments

`commands.argv_json` retains static shell word spellings, including quoting and assignment-shaped arguments after the command name (`-f title=hello`) but not prefix assignments (`FOO=1 env`), for flag questions such as `rg -rn`.

#### Results and freshness

Cells and column names are printed as stored, and text was redacted when it was indexed. Duplicate column names fail with an instruction to alias them uniquely. `sql` answers from what earlier commands indexed, and its `complete` covers only the rows its query selected from that: records those commands did not reach can be absent. To include them, run `sessidx index` first and check that its `end.stale` is `false`. `sql` probes the writer lock without waiting when it starts and does not hold it while reading; a writer holding it then sets `writer_busy=true` and leaves `stale=null` and `complete=true`. That writer may be partway through indexing, including a first build or `index --full`, so the committed rows can be a partial index. Narrow expensive queries to session paths or time windows.

### doctor

`doctor` names each count after the rows it counts, next to the population it belongs to: `files` and `incomplete_files`, `records` and `parse_errors` (records that did not parse, and compressed content that did not decode), `sessions` and `sessions_with_unknown_kind`, `events` and `canonical_events`, `tool_events` and `tool_events_without_model` (stored tool calls and results, inherited copies included; `count --by model` reports the canonical ones without a model as `unknown`), `shell_calls` and `shell_calls_unparsed`, and `denials` and `denials_with_unknown_reason`. A session count is not a human-conversation denominator.

## Refresh

`search`, `grep`, `show`, `count`, and `doctor` refresh with a two-second budget; `index` refreshes without one, and `sql` does not refresh. Refresh coverage reports writer contention, missing roots, and parse errors. A refresh with a budget waits within it for a writer that holds the lock, then refreshes with the rest; one that cannot take the lock before the budget runs out reports `writer_busy` and `stale`, and the query answers from committed data. `index` and `sql` do not wait for the lock. SQLite busy waits are limited to 50 ms. A refresh removes the rows of vanished transcripts after indexing new records, then reindexes the transcripts an earlier release's parser indexed, within the same budget; until it finishes, those transcripts answer from their earlier rows and the refresh reports `stale` with a `continuation`. A refresh also recreates views that an earlier release defined differently; when indexes differ too, only `index` builds them, and until then a refresh with a budget indexes nothing and reports `stale` with a `continuation`. Filesystem operations and individual SQLite operations can exceed a deadline, so the budget is not a hard end-to-end guarantee. `search` and `grep` have two seconds of their own after the refresh, so either can run about four seconds before it answers. A normal unterminated final record is deferred until its newline arrives, separately from staleness. `index --full` rebuilds derived data and its schema under the writer lock. `index` then compacts the database when more than half of its records were written since it was last compacted, as after a rebuild, a first index, or an upgrade that changed how records are read; compaction needs free disk space up to twice the database size while it runs, and when it fails, the index still answers queries and the error says so. A refresh before a query never compacts, so an index that only queries refresh comes due once it holds more records written since its last compaction than before it, and reads that are not cached stay slower until `index` runs; a `search` that then exceeds its limit says to run it.
