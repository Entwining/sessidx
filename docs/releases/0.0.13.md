Claude Code does not update plugins from third-party marketplaces by default, so run `claude plugin update sessidx@entwining`, or enable auto-update for the `entwining` marketplace under `/plugin` as the README describes. Codex updates the plugin when it starts, and Pi updates with `pi update git:github.com/Entwining/sessidx`. The skill now says that `sql` refreshes like the other commands, how to read a known session's conversation with `sql`, what `failed` counts, and how to filter output with `jq` without dropping the `end` record.

`sql` now refreshes the index within the same two-second budget as the other queries before it runs, so its answer includes what the logs gained since the last command, and its `end` reports `stale` and `writer_busy` as theirs do: `stale: false` once the refresh reached every log, and `stale: true` with `complete: false` when another process held the index lock for the whole budget. Running `sessidx index` before `sql` is no longer needed, and `sql` without an index starts building one, as the other queries do, instead of failing. A `sql` call now also takes the refresh's time, and when the refresh and the query both use their two seconds, about four seconds. Because the refresh indexes the running call itself, a query over every session's text, such as `text LIKE`, can match that call.

`search` shows each hit text longer than 512 bytes as the 512 bytes around its matches, and its session's `cut` gives the text's `bytes` and the `offset` and `kept` bytes shown. Before, it showed hit texts from their start, shortened to one length when a session did not fit a page. Search hits no longer repeat the `agent`, `session_id`, and `path` their session record carries, or the `line_no` their `ref` names: a `jq` filter that read `.hits[].path` reads the session's `.path` instead, and the line number is the part of `ref` after its last `:`. `grep` hits keep these fields.

`search` and `grep` no longer match the agent's own running `sessidx` call. A query's refresh indexed that call, whose text is the query, so a search for a rare word could return only the caller's own call. The line matches again once its result is indexed, and `show` and `sql` still read it.
