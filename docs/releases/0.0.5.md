Run `sessidx index --full` after upgrading. The schema version is now 8, and until the rebuild every command stops with `database schema changed; run sessidx index --full`.

Update the skill too. Claude Code does not update plugins from third-party marketplaces by default, so run `claude plugin update sessidx@entwining`, or enable auto-update for the `entwining` marketplace under `/plugin` as the README now describes. Codex updates the plugin when it starts, and Pi updates with `pi update git:github.com/Entwining/sessidx`. The skill now tells agents to run `sessidx` commands one at a time, because overlapping ones contend for the index lock and can come back stale and incomplete. It also corrects when a failure outcome is unknown, and names what agents got wrong in trials: `(?i)` for case-insensitive `grep`, one comma-separated `--by`, session selectors that match a whole ID or path rather than a prefix, UTC dates, and the columns of `sql` rows and `events`.

`search` no longer reads every event to fetch its hits, and `count failures` narrowed by time or session no longer groups every tool result in the history first. Both costs showed mostly with a cold page cache, as after an idle period. On the maintainer's logs a search took 0.7 to 1.3 s cold instead of about 6 s, and 0.16 s warm instead of 0.34 s; a one-week `count failures` took 4.5 s cold and 0.37 s warm instead of 8.2 s and 1.7 s, and a whole-history one by agent 1.6 s warm instead of 2.8 s. Counts over a fixed past range matched 0.0.4.

`call_outcomes` now has one row per canonical tool call, with the call's `id`, `agent`, `session_id`, `path`, `line_no`, `ts`, `role`, `model`, `tool`, `call_id`, and `file_id` beside `ok` and `ok_source`. A call without a result appears with a null `ok` and an `ok_source` of `none`, and results without a canonical call no longer appear; counts never included them. Narrow a query on the view by `ts` or session: an unfiltered query over all of it takes about 1.4 s warm on the maintainer's logs instead of 1.2 s.

A call's outcome now reads every result recorded with the call in its session, not only first copies of each result. A count can therefore move a call from unknown to known or from succeeded to failed, never the other way; on the maintainer's logs none moved.
