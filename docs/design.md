# Design

## Ownership and storage

One Rust package discovers four read-only session roots, two of them Codex's active and archived directories, and streams complete JSONL records through agent adapters. SQLite uses bundled FTS5, WAL with a 10,000-page autocheckpoint for the writer, foreign keys, an 8 MiB connection page cache, and an OS-released advisory writer lock. Persistent setup and schema writes happen only while holding that lock. An initialization race returns writer-busy coverage rather than bypassing the lock.

`files` owns its session, event rows, daily counts, and shapes; file IDs are never reused, so a cursor or frozen search order that names a file cannot reach its replacement. Each transcript file is one session: `sessions` holds its native identity, parent, kind, path, starting directory, and first timestamp, decided by the transcript's own header or name rather than by history copied into it, so an event belongs to the session of the file it appears in.

`event_rows` retains exact file/line/byte offset/length pointers, SHA-256 range digests, ordinals, native identity, timestamps, and the event's role, kind, model, tool, outcome, and their source labels inline; hashed event/call identities and range digests are 32-byte BLOBs. Context records have a row too, which filtered raw reads, `show path:line`, and native deduplication need. Each row also stores `line_role_first`, whether it is the first event of its role on its line, which grep and show display. Bodies live apart in `event_texts`, and the `events` view reads them through subqueries only when a query names `text` (`events_body_on_demand` in `docs/formats.md`). The view adds each event's agent, session ID, and path from its session, and lowercase hexadecimal hashes. Tool results retain pointers, outcomes, denial metadata, and a redacted text prefix of at most 2 KiB with a truncation flag. Unknown records retain a context pointer (location and range digest), their structural type/subtype/key signature, and coverage counts, never their body.

Token usage and compactions are rows of their own keyed by the event of their record. `usage_rows` holds what each record states about the tokens of its model request, with the event's file, timestamp and model repeated so that counts do not read `event_rows`, and `usage_passes` the passes of a request whose record lists several; `compaction_rows` holds a compaction's trigger, context sizes, and the usage of the calls that wrote its summary. A Claude response written as several records, or copied into another transcript, has a usage row per record, and the `requests` view reports one of them per request.

FTS indexes a Han-spaced copy of redacted message/input text and tool output prefixes in a contentless-delete table. The stored body exists only in `event_texts`; search hits read that body. The bundled SQLite supports DELETE on this contentless-delete table (added in 3.43.0), keeping the token positions phrase queries need. A delete does not lower the row count or total token length that BM25 ranking uses, so after files are replaced or deleted, ranking drifts slightly from a fresh build until `index --full`. Phrase queries preserve contiguous character order; Latin words retain `unicode61` semantics. Full tool outputs and deferred compaction/branch reconstruction remain outside FTS. Prefix extraction clips before redaction and again afterward if redaction expands the text; both cuts respect UTF-8 boundaries. Outcome classification still receives the complete result, independently of the stored prefix. Content-bearing Claude diagnostic attachments use the tool role and `tool_output` kind without inventing native tool results.

## Incremental indexing and recovery

An unchanged file needs matching device/inode, length, and nanosecond mtime/ctime, and a previous pass that did not run out of budget; one stat decides this without opening the file. A growing file resumes when device/inode and its stored prefix hash agree. Prefix length is stored, including files shorter than 4 KiB. Otherwise owned rows are replaced in one transaction. Carry state preserves session/model attribution across append refreshes. This follows the chosen append contract: a writer that changes old bytes beyond the prefix while also appending is not detected by the prefix test; range display still rejects changed bytes.

Codex can replace an idle rollout with a byte-identical `.jsonl.zst` sibling (its `local_thread_store_compression` feature or the `rollout/compress` request) and restores the plain file, then appends, when the thread resumes; archiving renames either form. A session file is identified by its plain `.jsonl` path: discovery maps `.jsonl.zst` to that path with one entry per pair, and opening tries the plain file, the compressed one, then the plain file again, because Codex publishes a new form before removing the old. Offsets, lengths and range digests address decoded bytes, so records keep their `path:line` across the change, and a change of form is a new inode that reindexes the file. Temporary files, multi-frame and undecodable content, and a file removed between discovery and opening follow the `session_file_names`, `zstd_multi_frame`, `invalid_zstd`, and `rollout_form_race` rows in `docs/formats.md`.

Claude/Pi content blocks already ignored by the adapters (thinking, images, and fallback) are validated as borrowed RawValue spans and reduced to their type before materialization. Multi-megabyte Pi thinkingSignature strings remain solely in the raw source; message identity/counts and byte digests are unchanged. Normal text, arbitrary tool inputs, and unknown block types still materialize normally. Records above 16 MiB are streamed past and counted as parse errors.

Only complete newline-terminated records advance the cursor. `index_status` distinguishes ready, deferred_tail, and budget_exhausted. A stable partial tail is not reread on every query, does not mean indexing failed, and resumes when the file changes. Explicit indexing is unbounded; a refresh before a query, run by the commands `docs/cli.md` lists under Refresh, receives two seconds, including discovery, and returns committed complete records with staleness and a continuation file. Filesystem operations and individual SQLite operations are not interruptible by this budget, which is why `docs/cli.md` calls the two seconds a budget rather than a guarantee. Part of every refresh grows with the number of transcripts rather than with what changed: discovery walks every root, each transcript is stat'ed and its `files` row read, and the coverage sums read every `files` and `shapes` row. On the maintainer's 9,096 transcripts that took about 0.16 s warm, 101 ms of it the walk, which took 285–292 ms when directory metadata was not cached. FTS5 merges its segments during inserts, so a refresh can also carry a merge larger than its own records; how large has not been measured.

The writer lock covers initialization, full reset, discovery reconciliation, and per-file transactions. A missing root that holds indexed files keeps its rows and prevents complete-coverage claims; one that never held any, such as an agent the user does not run or a Codex archive directory not yet created, does not affect coverage. A full rebuild refuses while such a root is missing, because its reset would drop the rows that keep later refreshes stale; recovery restores the root or rebuilds with `--root` for the roots that remain. Deleted files within present supplied roots lose their owned rows. Full rebuild drops derived child tables before source tables and recreates the schema transactionally, including a new index identity, then vacuums the empty database to release old pages. An unbudgeted `index` vacuums at its end once more than half of the indexed records were written since the last compaction, as after a rebuild, a first index, or a parser change, because one transaction per file interleaves the pages of every table and cold reads were bound by scattered page reads (`index_compaction` in `docs/formats.md`). A refresh before a query counts what it writes but never compacts, so in daily use without `index` the database comes due once its history has doubled since the last compaction, and cold reads stay scattered until `index` runs; the search deadline's error then names `index` as the recovery. FK event indexes also keep individual file replacement from scanning every command/denial row. A refresh deletes the rows of vanished files after indexing new records and stops at its budget between deletions (`refresh_budget`).

A normal open, including read-only SQL, rejects an older schema version with one recovery instruction, `run sessidx index --full`, and rejects an unknown version rather than treating it as an index owned by this binary. Explicit full indexing opens the old database, acquires the writer lock, and rebuilds derived tables; contention leaves the old schema intact. The sources are never migrated or modified. The schema version covers tables and triggers. Views and indexes carry no version: every refresh compares them with the binary's `schema.sql` and recreates the views that differ, and `index` builds the indexes that differ (`schema_definitions`). `sql` refuses views from another release with `run sessidx index`. How records become rows has a version of its own, recorded per file, and a refresh reindexes the files an earlier parser indexed after new records and deletions, within the same budget (`parser_version`). Only a table change needs a rebuild.

Display and scanning validate device/inode and the stored SHA-256 of the exact range; a range past the end of its source is unavailable. A plain source is read only at the range. A compressed one is decoded forward from its first frame, once per file for ranges in increasing order. A replaced, truncated, or rewritten range contributes unavailable coverage. A session filter first resolves a session ID or transcript path to one transcript, then selects its events by `file_id`. Grep selects transcripts from `sessions` by the session filters and by `min_ts`/`max_ts` against the time window, then reads each transcript's events in line order (`grep_traversal`). A grep progress handler covers SQLite preparation and stepping from the start of its scan budget; an interrupted step yields incomplete coverage and a continuation at the last event examined. Raw filesystem reads remain non-interruptible.

Cursors bind the query and filters to a cache identity, event high-water mark, invalidation revision and continuation: the last event examined for grep and show, with the offset where `show` resumes a record split across pages, and the number of frozen sessions passed, returned or no longer matching, for search. Appends cannot enter later pages. `index_changes` records each replaced or deleted file, and a cursor is refused only for a change to a file its later pages would read (`cursor_invalidation`); a full rebuild changes the identity and refuses all cursors. Search carries the initial session order because live FTS corpus statistics can rescore existing matches after appends. The order covers only the first 100 sessions, as their file IDs, so the cursor stays small however many sessions match, and a later page ranks hits only within the transcripts it shows. Hits within a selected session use current FTS scores over the bounded event set. A search stops after two seconds, which start when its refresh ends, so the two budgets add up (`search_deadline`). Cursor checks and the query share a SQLite read transaction.

`sql` performs no refresh. It probes the writer lock without waiting and releases it before reading (`sql_lock_probe`), and a SQLite progress handler enforces its two-second limit; its other limits are in `docs/cli.md`.

## Privacy and limits

Body text, tool inputs, and argv pass recall-leaning redaction once, before storage. Credential context is applied first: private-key blocks, Basic and Bearer authorization, known token prefixes and fixed-length token shapes, and values whose name marks a credential, in JSON fields, `name=value` and `name: value` assignments including multiword values and quotes with one backslash escaping layer, Cookie and Set-Cookie headers through the line end or enclosing argument quote, `key:` labels, and `--name value` flags. The name stays and its complete value is suppressed. A name marks a credential by its last word, after words that name the value's form such as `_value`, listed in the `docs/formats.md` row `credential_name`, so usage counters such as `input_tokens` keep their values. Values named as identifiers (`request_id`) get the credential patterns and named values only, and JSON keys the credential patterns only. Every remaining symbol/base62/base64-like run of at least 16 characters is then judged: multi-component absolute paths with up to two `:line` suffixes, email addresses, and runs made of identifier atoms survive; URLs keep their scheme and host and have each path segment and query value judged separately; any other run with Shannon entropy of at least 3.5 bits/character is suppressed whole. Each pattern and exemption is a row of the Redaction table in `docs/formats.md`. A smaller length or entropy cutoff redacts more aggressively. Han prose is outside the run detector.

Session IDs, models, tool/program names, and structural discriminators receive the credential patterns and named values without the run verdict. Source file paths and refresh continuation locations retain their exact spelling so callers can open them. These fields are operational metadata, not a place for credentials. A denial row takes the producer and reason a reason marker declares only when redaction leaves the marker unchanged, and otherwise keeps its class alone. Range display (`show`, `grep`) redacts the decoded JSON keys and values of the raw source the same way. What is read back from the index, such as `search` hits, `sql` cells and column names, `count` labels and `doctor` signatures, was redacted when it was stored and is printed as stored. No stored representation or diagnostic contains a raw output copy.

This is heuristic redaction, not a guarantee that all secrets can be recognized. An unmarked secret with a pure hexadecimal, UUID, absolute path or identifier-atom shape can survive; credential context or a known prefix is required for those values. This accepts unmarked random values made entirely of letters: for uniformly sampled alphanumerics, that subset is about 6% at length 16 and 0.36% at length 32, before accounting for additional atom-shaped values with trailing digits or all-digit atoms, such as a letter run followed by `-` and a digit group. Joining a random value to a word with `_`, `=`, `:` or another separator does not make it more likely to survive than the bare value. Redaction analyzes JSON values independently and does not reconstruct a secret split across fields; fragments that individually evade the patterns or entropy cutoff can remain recoverable together. Bare base64 below 16 characters is outside the run detector, and values of 16–23 characters still depend on the entropy cutoff; being shorter than 24 is not itself enough to determine redaction. Short/low-entropy secrets, non-ASCII credentials, and secrets disguised as operational metadata can also survive. A credential whose name does not end in a credential word (`pass`, `password_for_db`, `session`, `sid`) is not recognized by its name; cookie members under such names need a Cookie or Set-Cookie header or another credential context.

`search`, `grep`, and `show` pages hold at most 24 KiB of data lines. A `grep` or `show` record that alone exceeds a page is shown as pieces of its JSON text, which `show` continues through, and a `search` session shortens its hit texts. Cutting applies to the redacted value, so offsets never expose original bytes.

Synthetic shaped and unmarked non-hex high-entropy canaries cover user messages, tool inputs, outputs, the live database/WAL/SHM, every CLI command, stdout, and stderr. Context-labeled hex has separate controls. Those checks establish the tested partitions only. Any newly observed leaking canary is a failed gate, not proof that the heuristic is safe elsewhere.

## Counting and attribution

`events` preserves observed records. `canonical_events` chooses one event per agent/native ID/kind; absent IDs remain unique rows. Claude assistant fragments use message ID before transcript UUID; the kept row is a message's earliest fragment, and its `text` in `canonical_events` joins the text of every fragment in that transcript. Native IDs deduplicate inherited copies without comparing text, so independent identical messages and retries remain separate. The earliest first-record timestamp chooses copy ownership, with path/line/ordinal as deterministic ties. Each event is compared only with its own copies, so a query narrowed to a session or time range reads only those events and their copies. Missing or tied start timestamps cannot establish the true origin. Recorded parent IDs are retained, but no ancestry is invented and no Pi branch/context-edit reconstruction is performed.

Models come from Claude message metadata with carry-forward excluding `<synthetic>` as a switch, Codex turn_context, and Pi explicit message model/model_change. A synthetic assistant still retains its explicit synthetic model. A speaker role is separate from session kind and both preserve their field source. Session kind comes only from native evidence (`session_kind` in `docs/formats.md`); without it, kind is unknown. User-role messages can include injected instructions, so they are not necessarily human messages. Codex instruction hashes identify recorded base text, with injected AGENTS.md text as fallback; they do not prove instruction loading or adherence. Claude/Pi instruction inference is deferred.

Each CLI metric counts one population, named in its fields, and its counts partition that population; what lies outside it has a name of its own:

| Metric | Population | Parts | Outside the population |
| --- | --- | --- | --- |
| commands | Parsed static sites (`sites`) | `sites_without_program`; with `--program`, `matching_sites` | `unparsed_calls` |
| failures | Native tool calls (`calls`), with `--program` those whose syntax names it | `failed`, `succeeded`, `outcome_unknown` | With `--program`, `calls_with_unresolved_program` |
| denials | Native tool-result events (`results`), with `--program` those of calls naming it | `denied`, of which `denied_reason_unknown` | With `--program`, `results_with_unresolved_program` |
| usage | Model requests recorded with usage (`requests`), and the passes they ran (`passes`) | Token sums over passes, each optional field with the passes that record it | Records without usage, such as Pi cache warm-ups and Claude's synthetic replies |
| compactions | First copies of compaction records (`compactions`) | `auto`, `manual`, `trigger_unknown` | Codex `compaction` response items |

Whether an event is the first copy of its native event, what a tool call's outcome is, which call a tool result answers, and which usage record a request reports depend on other rows, including rows of other transcripts, so each per-file transaction recomputes them for the keys its rows touch and stores them in `event_rows` and `usage_rows` (rules `derived_facts`, `call_pairing`, and `usage_snapshot`). `daily_counts` sums, per transcript, UTC day, kind, role, model and first-copy flag, what `count` and `doctor` report, and `daily_program_counts` sums the same first-copy calls and results once per program their call's sites name; the same transaction applies its changes to both as deltas, adding its own rows once their derived columns are settled (rules `daily_counts` and `rollup_work`). `count` and `doctor` read whole days from them and the part of a day at either edge of a window from the events, with or without `--program`. `count_view_parity` in `docs/formats.md` keeps them equal to the same counts written plainly over the views. `count usage` and `count compactions` read the `requests`, `request_passes`, and `compactions` views themselves, with no rollup (`count_usage`).

A denial event with multiple envelopes counts once in `count`; `denials` preserves individual recognized source/reason rows for SQL. An outcome comes only from evidence: Claude and Pi error flags, and for Codex, decoded shell transports, the MCP transport `isError`, leading script/process prefixes, and Promise rejections. Failed evidence wins when several result records join the same agent/session/call identity, results with no qualifying evidence remain unknown, and no per-command exit status is inferred: generic inner error wording is not a failure, exit zero does not classify every inner command, and transport stdout is not recursively treated as another result. Which text qualifies, and why, is in the Outcomes and denials rows of `docs/formats.md`. A denial's class, producer and reason come from a reason marker when one begins its slot, else a frozen table of published guard sentences that never gains rows, maps to agent-guard's public reason IDs with the dotfiles guards' names for rules only they had, keeps a shared sentence's class with reason `unknown`, and leaves unmapped text `unknown`; the table covers only the maintainer's past guards and declares no producer. Pi bare-reason recognition is separate from reason classification, and Pi's own default block text is native hook evidence.

Some counts need data v1 does not persist: per-batch-item results, full output-block classification, branch diagnostics, and inner stderr failure heuristics. They cannot be reproduced through SQL from output prefixes and pointers; answering them means reading raw ranges with `grep` or `show`, not extending the schema to copy outputs or reporting zeros.

## Shell command sites

Brush walks simple commands, pipelines, conditions, loops, functions, command/process substitutions, and expandable heredocs. This measures syntax sites, including untaken branches and function bodies. It does not resolve aliases, `env`/`command` wrappers, quoted shell `-c` bodies, dynamic programs, parameter/arithmetic expansions, or extended-test substitutions.

Codex exec wrappers are JavaScript. A regex locator takes only literal `cmd` fields of direct tools.exec_command object calls and decodes them by the [ECMAScript string and template value rules](https://tc39.es/ecma262/multipage/ecmascript-language-lexical-grammar.html#sec-literals-string-literals); a wrapper that references a shell tool but yields no parsed site from a literal keeps one opaque site. Metadata scanning skips a single level of nested objects and flat arrays. Which spellings, escapes, and overriding members it accepts is in the Shell sites and Codex code mode rows of `docs/formats.md`. Regex extraction does not validate the entire JavaScript source and can recover a literal call despite malformed syntax elsewhere. It never evaluates JavaScript or resolves names/aliases.

Parser refusals, sources above 256 KiB and Brush traversal beyond depth 64 remain unparsed. These limits and `unparsed_calls` must accompany program-frequency claims; static sites never establish executions.

## Dependencies

All direct versions and `Cargo.lock` are pinned. A crate is added only where it replaces code that would otherwise be hand-written; the standard library's nonblocking File locks made a locking crate unnecessary.

`about.toml` and `about.hbs` describe the license notices of the crates compiled into the binary. `make build OUT=DIR` stages the package: the binary, `LICENSE`, `README.md`, and `LICENSE-THIRD-PARTY.md` rendered from them. The Homebrew formula installs that package. CI builds the package too, so a license they cannot place, or a notice cargo-about drops with only a warning, fails before a release rather than during one.
