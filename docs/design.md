# Design

## Ownership and storage

One Rust package discovers three read-only session roots and streams complete JSONL records through harness adapters. SQLite uses bundled FTS5, WAL, foreign keys, an 8 MiB connection page cache, and an OS-released advisory writer lock. Persistent setup and schema writes happen only while holding that lock. An initialization race returns writer-busy coverage rather than bypassing the lock.

`files` owns locations, event details, sessions, and shapes. `locations` retains exact file/line/byte offset/length pointers, SHA-256 range digests, ordinals, native identity, timestamps, and model/session references. Locations and event details store hashed event/call identities and raw-range digests as 32-byte BLOBs. Repeated metadata, including session IDs and source labels, is interned as integer references in `strings`. `event_details` exists only for logical events; context locations derive their constant role, kind, and missing outcome fields. These locations remain necessary for filtered raw reads, `show path:line`, and native deduplication. The `events` view exposes the original textual columns and lowercase hexadecimal hashes to queries. The string lookup cache is local to each file transaction, so a rollback cannot leave cached references to uncommitted rows. Tool results retain pointers, outcomes, denial metadata, and a redacted text prefix of at most 2 KiB with a truncation flag. Unknown records retain only structural type/subtype/key signatures and coverage counts.

FTS indexes a Han-spaced copy of redacted message/input text and tool output prefixes in a contentless-delete table. The stored body exists only in events; search snippets read that body. Bundled SQLite 3.46.0 supports ordinary FTS deletes while retaining token positions and BM25 statistics. Phrase queries preserve contiguous character order; Latin words retain `unicode61` semantics. Full tool outputs and deferred compaction/branch reconstruction remain outside FTS. Prefix extraction clips before redaction and again afterward if redaction expands the text; both cuts respect UTF-8 boundaries. Outcome classification still receives the complete result, independently of the stored prefix. Content-bearing Claude diagnostic attachments use the tool role and `tool_output` kind without inventing native tool results.

## Incremental indexing and recovery

An unchanged file needs matching device/inode, length, and nanosecond mtime/ctime. A growing file resumes when device/inode and its stored prefix hash agree. Prefix length is stored, including files shorter than 4 KiB. Otherwise owned rows are replaced in one transaction. Carry state preserves session/model attribution across append refreshes. This follows the chosen append contract: a writer that changes old bytes beyond the prefix while also appending is not detected by the prefix test; range display still rejects changed bytes.

Claude/Pi content blocks already ignored by the adapters (thinking, images, and fallback) are validated as borrowed RawValue spans and reduced to their type before materialization. Multi-megabyte Pi thinkingSignature strings remain solely in the raw source; message identity/counts and byte digests are unchanged. Normal text, arbitrary tool inputs, and unknown block types still materialize normally. Only complete newline-terminated records advance the cursor. `index_status` distinguishes ready, deferred_tail, and budget_exhausted. A stable partial tail is not reread on every query, does not mean indexing failed, and resumes when the file changes. Records above 16 MiB are streamed past and counted as parse errors. Explicit indexing is unbounded; refresh on search/show/count/doctor receives two seconds, including discovery, and returns committed complete records with staleness and a continuation file. Filesystem operations and an individual SQLite operation are not interruptible by this deadline, so two seconds is a refresh budget rather than a strict end-to-end latency guarantee.

The writer lock covers initialization, full reset, discovery reconciliation, and per-file transactions. Missing roots preserve their existing rows and prevent complete-coverage claims. Deleted files within present supplied roots lose their owned rows. Full rebuild drops derived child tables before source tables and recreates the schema transactionally, then vacuums the empty database to release old pages; FK event indexes also keep individual file replacement from scanning every command/denial row.

Schema version 3 adds prefix truncation to the compact layout. A normal open, including read-only SQL, rejects versions 1 and 2 with one recovery instruction: `run sessidx index --full`. Explicit full indexing opens the old database, acquires the writer lock, and rebuilds derived tables; contention leaves the old schema intact. The sources are never migrated or modified. Unknown schema versions are rejected rather than treated as an index owned by this binary.

Display and scanning validate device/inode, length, and the stored SHA-256 of the exact range. They never read a file prefix or unrelated source record. A replaced, truncated, or rewritten range contributes unavailable coverage. Shared session filters first resolve strings/file paths through their unique indexes, then select location IDs through session/file indexes. A grep progress handler covers SQLite preparation and stepping from the start of its scan budget; an interrupted first step yields incomplete coverage and an unchanged continuation. Raw filesystem reads remain non-interruptible. Raw regex matching precedes display redaction; grep/show pagination retains an event cursor and incomplete coverage in the final JSON record. Cursors bind the query and filters to a file-metadata fingerprint; refresh changes invalidate them. The query and fingerprint share a SQLite read transaction. SQL performs no refresh, holds a nonblocking shared lock when the writer is idle, and marks reads stale/incomplete when the writer lock is held. Duplicate output names after redaction require unique aliases. It runs one readonly SELECT/WITH with a two-second progress handler and 10,000-row result bound; exceeding either fails the operation.

## Privacy and limits

Body text, tool inputs, and argv pass recall-leaning redaction before storage. Patterns cover private-key PEM blocks, Bearer/Basic authorization, known token prefixes, credential assignments/headers including key:, and quoted multiword values. JSON objects are decoded first, and credential-like keys suppress their complete values. Pure hex, 0x-prefixed hex, UUID shapes and absolute paths survive entropy alone. Remaining base62/base64-like runs of at least 16 characters with Shannon entropy at least 3.5 bits/character are suppressed. A smaller length or entropy cutoff redacts more aggressively. Han prose is outside the run detector.

Session IDs, models, tool/program names, and structural discriminators receive recognizable-pattern redaction without body entropy suppression. Source file paths and refresh continuation locations retain their exact spelling so callers can open them. These fields are operational metadata, not a place for credentials. Range display redacts decoded JSON keys and values again; SQL and diagnostics redact their textual output. No stored representation or diagnostic contains a raw output copy.

This is heuristic redaction, not a guarantee that all secrets can be recognized. An unmarked secret with a pure hexadecimal, UUID or path shape can survive; credential context or a known prefix is required for those values. Redaction analyzes JSON values independently and does not reconstruct a secret split across fields; fragments that individually evade the patterns or entropy cutoff can remain recoverable together. Bare base64 below 16 characters is outside the run detector, and values of 16–23 characters still depend on the entropy cutoff; being shorter than 24 is not itself enough to determine redaction. Short/low-entropy secrets, non-ASCII credentials, and secrets disguised as operational metadata can also survive. Structured value recognition can over-redact ordinary keys containing `token` or `secret`. Raw logs remain the user's existing source; no real lines are copied into fixtures, documentation, or reports. Synthetic shaped and unmarked non-hex high-entropy canaries cover user messages, tool inputs, outputs, the live database/WAL/SHM, every CLI command, stdout, and stderr. Context-labeled hex has separate controls. Those checks establish the tested partitions only. Any newly observed leaking canary is a failed gate, not proof that the heuristic is safe elsewhere.

## Counting and attribution

`events` preserves observed records. `canonical_events` chooses one event per harness/native ID/kind; absent IDs remain unique rows. Claude assistant fragments use message ID before transcript UUID. Native IDs deduplicate inherited copies without comparing text, so independent identical messages and retries remain separate. The earliest first-record timestamp chooses copy ownership, with path/line/ordinal as deterministic ties. Missing or tied start timestamps cannot establish the true origin. Recorded parent IDs are retained, but no ancestry is invented and no Pi branch/context-edit reconstruction is performed.

Models come from Claude message metadata with carry-forward excluding `<synthetic>` as a switch, Codex turn_context, and Pi explicit message model/model_change. A synthetic assistant still retains its explicit synthetic model. A speaker role is separate from session kind and both preserve their field source. Only explicit Claude sidechain/Codex subagent evidence produces delegated kind; otherwise kind is unknown. User-role messages can include injected instructions, so they are not necessarily human messages. Codex instruction hashes identify recorded base text, with injected AGENTS.md text as fallback; they do not prove instruction loading or adherence. Claude/Pi instruction inference is deferred.

The three CLI metrics use different units:

| Metric | Numerator | Denominator | Unclassified |
| --- | --- | --- | --- |
| commands | Parsed static sites, optionally selected by program | All parsed static sites in the filter | Unparsed shell calls or sites with unresolved program |
| failures | Selected native calls with failed call-level result | Selected native calls, including missing results | Missing outcome or unresolved program selection |
| denials | Selected native result events with qualified denial metadata | Selected native result events | Unknown denial reason or unresolved program selection |

A denial event with multiple envelopes counts once in `count`; `denials` preserves individual recognized source/reason rows for SQL. Claude/Pi booleans provide flag evidence. Codex decoded shell transports (including custom-labeled transport objects), MCP transport isError, leading script/process prefixes, and Promise rejections provide text evidence. A transport Boolean is distinct from a native Codex error flag; failed items win over later successful items. Complete rejection fields after a parsed value in a truncated block remain qualifying evidence. Generic inner error wording is not a failure, exit zero does not classify every inner command, and transport stdout is not recursively treated as another result. Results with no qualifying evidence remain unknown. Failed evidence wins when multiple result records join the same harness/session/call identity; no per-command exit status is inferred. Codex hook markers must be the first nonempty payload line after a leading Script error header; later file-dump quotations do not qualify. Claude permission-refusal text without a native mechanism is labeled native_denial, not classifier. Textual leading reason sentences map to stable reason IDs and may recognize historical wording that does not equal the complete current guard constant.

Brush 0.4.0 walks simple commands, pipelines, conditions, loops, functions, command/process substitutions, and expandable heredocs. This measures syntax sites, including untaken branches and function bodies. It does not resolve aliases, `env`/`command` wrappers, quoted shell `-c` bodies, dynamic programs, JavaScript `tools.exec_command` literals, parameter/arithmetic expansions, or extended-test substitutions. Opaque exec wrappers mentioning shell tools receive an unparsed-call row. Parser refusals, inputs above 256 KiB, and traversal beyond depth 64 remain unparsed. These limits and the unparsed denominator must accompany program-frequency claims; static sites never establish executions.

The independent gold adds units not persisted by the v1 decision, including nested JavaScript sites, per-batch-item results, full output-block classification, branch diagnostics, and inner stderr failure heuristics. These cannot be reproduced through v1 SQL from output prefixes and pointers. The implementation report marks those rows unavailable and separates them from supported numeric differences rather than extending the schema to copy outputs or inventing zeros.

## Dependencies and validation

All direct versions and Cargo.lock are pinned. The decision specifies Brush, bundled rusqlite, and serde_json. Additional crates remove real code: serde derives persisted state/output; anyhow removes error-conversion boilerplate; regex supplies scan/redaction matching; chrono supplies timestamps/weeks; sha2 supplies fingerprints; walkdir replaces recursion; clap supplies CLI validation. Standard-library File locks are nonblocking and released on close. Test-only tempfile owns isolated fixture/database cleanup. rusqlite hooks provide the SQL deadline, and its existing statement cache avoids preparing per-record INSERTs again. The serde_json raw_value feature avoids owned decoding of opaque blocks.

Fixtures are synthetic. Tests protect message/site counts, flags and quoted-output controls, native identity and model attribution, append/truncate/replacement equivalence, same-size mtime-preserving rewrites, initialization contention, deferred tails, exact ranges, CJK/Latin retrieval, secret canaries, and readonly SQL. Ablation temporarily removes each listed rule and requires an assertion failure plus an unrelated passing control. Classification-only auxiliary rules change known/unknown record counts; they do not establish a logical-message counting mechanism. Real-corpus performance and frozen gold/lookup results belong in the acceptance report and are not inferred from unit tests.
