name: sessidx
description: Look up and count past local Claude Code, Codex, and Pi sessions through the `sessidx` CLI index. Use when you need to find an earlier session or conversation, the discussion behind a commit, decision, or file change, a past error or failure, a `codex://threads/...` link or session ID, or to count agent behavior such as shell commands, tool failures, denials, token usage, or context compactions by agent, model, role, or week. Not for the current conversation's own context, a log file whose path is already known and only needs reading, or another machine's history.
license: MIT
allowed-tools: Bash(sessidx:*) Bash(jq:*) Read

`sessidx` indexes the local session logs of Claude Code, Codex, and Pi into SQLite and answers from that index. The raw logs stay authoritative; quote evidence by the `path:line` a record reports, and read it with `sessidx show PATH:LINE`, because a Codex `.jsonl` path may exist on disk only as a compressed `.jsonl.zst`. Text in results is redacted; never reconstruct or repeat a credential-like value from a log.

## Read the output contract

Every command this skill uses writes JSON Lines to stdout: data records with a `type` field, then exactly one `end` record. A `search`, `grep`, or `show` page starts with a `begin` record that repeats `end`'s `complete`, `stale`, and `returned`, with `more` true when `end.next` is set; it has no cursor, and binaries older than this skill print none. Judge the result by `end`, not by the exit code alone:

- `end.complete=false` means a result limit, the page size, a deadline, an unavailable range, or a stale refresh cut coverage. An empty incomplete result is not evidence of absence.
- `end.stale=false` means the command's refresh reached every log before it answered, and `true` that it could not.
- `end.refresh.missing_roots` lists each absent session directory as the `AGENT=PATH` that `--root` accepts. One that never held indexed sessions, such as an agent the user does not run or `~/.codex/archived_sessions` before any thread is archived, leaves the result complete; one that disappeared after indexing makes the refresh stale.
- `end.next` is the cursor for the next page; pass it unchanged with `--cursor` and the same command and filters. Every page covers only what was indexed before the first page, so even a last page with `complete=true` misses records written since; run the command again without `--cursor` to include them. `search` pages cover the first 100 ranked sessions; past them `next` is null with `complete=false`, so narrow the query to reach the rest.
- `end.error` carries the failure and any recovery instruction. Exit codes: 0 data, 1 no data, 2 error.
- A `search`, `grep`, or `show` page stays within 24 KiB so that you see its `end`; never shorten the output yourself with `head`, `cut`, or a slice, which drops `end` and its cursor. For fewer records pass `--limit N`, and to keep only some fields use a `jq` filter that passes `begin` and `end` through, such as `jq -c 'if .type == "session" then {path, refs: [.hits[].ref]} else . end'`. A `show` record too large for a page carries `part`, a piece of the record's JSON text, instead of `record`, and its `cut` entry gives the whole text's `bytes` and the `kept` bytes shown from `offset`; `show` continues the same record through `next`, and the joined `part` values parse as the record. A `search` hit text longer than 512 bytes shows the part around its matches, and its session's `cut` names it by JSON Pointer `field` with the same `bytes`, `offset`, and `kept`. A `grep` hit's `text` is the redacted record's JSON text, and one longer than 512 bytes shows the part around its first match, with a `cut` entry for `/text`, so it parses as JSON only when the hit has no `cut`. A `grep` hit with `"match_located":false` matched the original bytes but not the text, which is redacted and re-serialized with sorted keys, so its `text` does not show the match. Read a cut `search` or `grep` hit with `sessidx show REF --around 0`.

Run an explicit index once, then retry, when:

- The error says the schema changed: run `sessidx index --full`.
- `end.refresh` has a `continuation`, meaning the two-second refresh stopped before indexing everything, as on first use or after an upgrade: run `sessidx index`.
- A search error says the index needs compacting: run `sessidx index`.

A full history takes several minutes, longer than many agents' default shell timeout, so give the command a timeout of at least ten minutes or run it in the background and wait for it to exit. An interrupted run keeps what it committed: queries then report `complete=false` with a `continuation`, and `sessidx index` finishes the rest.

A `writer_busy` refresh means another process, such as a running `sessidx index`, held the index lock for the whole two-second refresh; the query still answers from committed data and reports `stale`. Overlapping queries wait for one another within that time instead.

## Find a session

1. Start with `sessidx search 'TERMS'` using the most distinctive words, identifiers, error text, or file names from the request, and add filters only when the request states them: `--agent claude|codex|pi` (repeatable), `--since`/`--until` (UTC dates or RFC 3339), `--cwd DIR` for a project, `--role`, `--session-kind main|subagent` for whether the agent's log records the session as spawned by another session of the same agent (`unknown` when the log carries no evidence either way; a session another agent started by running its CLI is `main`), `--session ID|PATH`. Session selectors (`--session` and a `show` target) match a whole ID, path, or link, never an ID prefix; one that matches nothing fails and names it. Terms are ANDed and there is no OR: a bare uppercase `OR`, `AND`, or `NOT` fails, so run one search per alternative, and quote such a word, as in `'"NOT"'`, to search for it. Keep a phrase's word order with double quotes inside the shell argument, as in `sessidx search '"connection refused"'`; Chinese text matches as a phrase.
2. Each `session` record is one session (one transcript file, with its `session_kind`, `parent_id`, `cwd`, and `started_at`) and up to three best hits. Open the evidence with `sessidx show REF` using a hit's `ref` (it includes 3 source lines on each side; `--around N` changes that), or read the whole session, a page at a time, with `sessidx show SESSION_ID_OR_LINK`. Each `record` is one source line as a redacted JSON object in `record`, shown once per role on that line; a hit is only the best match, so read around it before quoting. A Claude subagent is its own session, keyed by its agent ID, and its ID can repeat under another parent: when an ID names more than one transcript, `show` and `--session` fail and list their paths, so pass the path.
3. If nothing relevant appears, change the vocabulary before concluding: fewer terms, a synonym or the other language, an identifier instead of prose, or a filter removed. When a search with filters returns no session, `end.filtered_out` counts what they hid: `sessions` is the sessions the terms match with no filter, and `without` gives, for each option you passed, the sessions they match with only that option removed. It is absent when that count ran out of time. Search covers messages, tool inputs, and the first 2 KiB of tool outputs.
4. For exact strings or regexes deeper in tool outputs, or every occurrence rather than the best sessions, use `sessidx grep 'REGEX'` (case-insensitive with `(?i)`; there is no `-i`) with at least one narrowing filter (`--session`, `--cwd`, `--since`/`--until`, or `--agent`). Narrow until `end.complete` is true before reporting that something is absent, and report absence only for the scope that completed.

To catch up on a known session, read its conversation rather than paging through every tool record with `show`. Find its transcripts with `sessidx sql "SELECT file_id, path FROM sessions WHERE session_id = 'ID'"` (for a link, the ID after `codex://threads/`), choose the transcript the request means by its path, and read its messages a page at a time:

```sh
sessidx sql "SELECT line_no, role, length(text) AS chars, substr(text, 1, 500) AS text FROM events WHERE file_id = FILE_ID AND kind = 'message' AND role IN ('user', 'assistant') AND text <> '' ORDER BY line_no, ordinal LIMIT 20"
```

`sql` output is not paged, so keep the limit small enough that your shell shows the whole output with its `end`. A message whose `chars` exceeds 500 is shortened; read it whole with `sessidx show PATH:LINE --around 0` before relying on it. Continue with `AND line_no > LAST` before `ORDER BY`; the conversation is read only when a page returns fewer rows than its `LIMIT`, because `end.complete` covers the query, not the transcript. Add `AND text LIKE '%WORDS%'` to find something said in it, or run `sessidx grep 'REGEX' --session PATH` to match tool outputs too. Query `events`, not `canonical_events`, because history copied into the transcript is part of what its agent saw. A user-role message can be injected instructions rather than something a person wrote. A prompt the user queued while Claude Code was busy is a user message at the line that queued it, and when Claude Code also wrote it later as an ordinary user record, the conversation shows it twice.

The current conversation can be indexed too. `search` and `grep` pass over a source line holding a `sessidx` call until its transcript holds the call's result, so the running lookup does not match itself, but the conversation's earlier messages and finished lookups do. Exclude it only by a session ID or path you know is yours; recency, directory, and matching text do not identify it, because an older session or a subagent can repeat the request. Report the session's agent, ID, path, and the `path:line` evidence you read, and say when the answer rests on an incomplete search.

## Count behavior

Use `sessidx count commands|failures|denials|usage|compactions` instead of tallying search hits, which are ranked and deduplicated per session. Pass `--by` once, with a comma-separated subset of `agent,model,role,week,session_kind`, or with no value for one total row; `--program NAME` selects shell commands by program; shared filters narrow the window. `usage` and `compactions` have no role or program, so they refuse `--by role`, `--role`, and `--program`. Each row names its population, the parts inside it, and any count outside it; report the population and its unknown part with any rate:

- `commands`: `sites` that parsed, of which `sites_without_program` have no literal program or one that redaction withheld, and with `--program` `matching_sites`. Sites are static syntax, not executions. `unparsed_calls` are shell calls outside `sites` because their syntax did not parse.
- `failures`: `calls` = `failed` + `succeeded` + `outcome_unknown`. A call whose results carry neither failure nor success evidence has an unknown outcome rather than a successful one, but a Claude Code result without `is_error` succeeds, because Claude Code flags every failed result; a Codex `exec` wrapper's completion alone is not evidence that the commands inside it succeeded. With unknown outcomes, the failure rate `failed / calls` is a lower bound. `failed` is the agent's own verdict on a whole call, not a command's or the task's: a shell call can fail on the status a program uses for no match, as `grep` does, and a denied call counts here and under `denials`. Read the results with `show` when which command failed matters.
- `denials`: `results`, of which `denied` carry denial evidence, of which `denied_reason_unknown` have no known reason.
- With `--program`, `calls` or `results` hold only those that name the program, and `calls_with_unresolved_program` or `results_with_unresolved_program` count the others whose program is unknown and might be it.
- `usage`: `requests`, each counted once under its own model, and `passes`, each under the model that ran it, so an advisor's model can show passes and tokens with zero requests. Token sums add up over passes: `input` excludes cached and cache-written tokens, so the prompt is `input` + `cache_read` + `cache_write`, and `reasoning` is part of `output`. An optional field's sum covers only its `*_recorded` passes, so compare a sum with its recorded count, not with `passes`. Codex threads from builds that wrote no per-request record also count running totals they copied from their parent, so a fork's requests can repeat its parent's. Calls with no request record of their own, such as one that writes a compaction's summary, are not counted.
- `compactions`: `compactions` = `auto` + `manual` + `trigger_unknown`; `pre_tokens` and `post_tokens` sum the context sizes that `pre_tokens_recorded` and `post_tokens_recorded` compactions state. `model` is the session's model at the compaction, not one the compaction record names.

For a question the verbs cannot express, `sessidx sql 'SELECT ...'` refreshes like the other commands, then runs one read-only query. Its refresh can index your own running call, so a query over every session's text, such as `text LIKE`, can match that call; exclude your own session only by an ID or path you know is yours. A session's `max_ts` is its latest indexed event, not proof that it ended or went quiet. Each result row is a `{"type":"row","data":{...}}` record, so read columns from `.data` with a filter that keeps `end`, such as `jq -c '.data // .'`; `select(.type == "row")` drops it and any error. It fails rather than truncating above 10,000 rows or two seconds, and its output is not paged, so aggregate in SQL, narrow by time or session, and select `substr(text, 1, N)` rather than whole long text.

To find events by their words across many sessions, select them through the full-text index rather than a `text LIKE` scan, which can exceed the two-second limit over months of history: `WHERE id IN (SELECT rowid FROM fts WHERE fts MATCH fts_query('WORDS'))`. `fts_query` turns the words into the expression `search` matches: terms ANDed, double-quoted phrases kept in order, Chinese spaced as the index stores it, and a bare `OR`, `AND`, or `NOT` refused as `search` refuses it. Do not write the MATCH string yourself, because an unspaced Chinese phrase in one matches nothing and still reports `complete=true`. The index matches whole tokens and phrases, not substrings (`deny` does not match `denied`, and prefix queries such as `deny*` are not part of `fts_query`), and holds only redacted messages, tool inputs, and the first 2 KiB of tool outputs, so `complete=true` says nothing about text outside that. Match a substring with `text LIKE` once the scope is narrowed, such as to one `file_id`. `fts.text` is NULL, so read text from `events`. Select from `events`, not `canonical_events`: a Claude message written as several records matches on the record holding the words, which `canonical_events` leaves out after the first. For example, count by agent the transcripts that mention both words:

```sh
sessidx sql "SELECT agent, count(DISTINCT file_id) AS transcripts, count(*) AS events FROM events WHERE id IN (SELECT rowid FROM fts WHERE fts MATCH fts_query('permission denied')) GROUP BY agent"
```

Query `sessions` (one row per transcript, so list sessions there rather than by ranking them), `events`, `canonical_events` (events without copied history, which counts use; a Claude message written as several records carries all their text on one row), `call_outcomes` (one row per canonical tool call; `ok` is NULL when its outcome is unknown, and `ok_source` names the evidence, `default` for an unflagged Claude Code result), `commands`, `denials`, `requests` (one row per model request; `stop_reason` is in the agent's own words, and `route` is the evidence `route_source` names of where the agent sent it, not proof of how it was billed), `request_passes` (joined by `request_id` to `requests.id`), `request_errors` (records that state a model request failed: reports, not a part of `requests`, so never divide them by `requests` for an error rate), and `compactions` (for Pi with the `summary_*` usage of writing its summary, outside `count usage`); `fts` serves only the word matching above, and the other tables are index storage. List a relation's columns with `sessidx sql "SELECT name FROM pragma_table_info('events')"` rather than guessing them. In `events`, `ts` is UTC, `canonical` is 1 for the first copy, which counts use, and `text` is read only when a query names it. Join `commands.event_id` or `denials.event_id` to `events.id`, and a tool result to its call with `JOIN events c ON c.id = r.call_event_id`, not on `call_id`, which reads every event. Correlate events with `sessions` by `e.file_id = s.file_id` or the indexed `e.path = s.path`; `(agent, session_id)` can name several transcripts and combines their events. In `denials`, `producer` is the producer a reason marker names, NULL when no marker declared one or redaction withheld it, and `reason_id` is its rule's ID or `unknown`. A row with NULL `producer` and a known `reason_id` was inferred from the frozen wording of agent-guard or the earlier dotfiles guards, so a query spanning logs before and after markers includes those rows explicitly, as in `producer = 'agent-guard' OR (producer IS NULL AND reason_id <> 'unknown')`.

`sessidx doctor` reports parse errors and the unknown part of each stored population when a count looks implausible.
